이벤트 노트 메모리 연구: 단계별 상세 기록 (2026-10-18 ~ 10-28)
=====================================================================
작성: 2026-10-28. 원본 기록은 research/LOG.md, 코드는 research/notes_vlm/, research/lrbridge/server.py,
research/seqpol/evaluate.py. 과제 번호 tXX는 MIKASA-Robo 과제 목록 순번
(t50/t51/t52 = 색 기억 3/5/9색 Long 버전, t54 = 모양 기억 5 Long, t65 = 색 순서 3 Long).


0. 문제 설정과 공통 조건
-------------------------
과제 (RememberColor-N-Long, t50/t51/t52)
  - 첫 장면: 테이블 가운데 큐 큐브 1개. 128x128 상단 카메라에서 약 4픽셀.
  - 약 100 step 뒤 큐가 사라짐 → 수백 step 동안 빈 테이블 → 후보 큐브 N개(3/5/9)가 원형으로 등장
    → 큐와 같은 색 큐브를 터치하면 성공. 에피소드 최대 600 step.
  - 큐가 사라진 뒤 수백 step을 기억해야 하므로, 현재 프레임만 보는 정책은 찍기 수준(1/N)이 상한.
  - 9색에는 Red, Lime, Blue, Yellow, Magenta, Cyan, Maroon(어두운 빨강), "Olive"(실제 RGB는 주황
    255,128,0), Teal(어두운 청록)이 있어 비슷한 색 쌍이 3개(빨강/적갈, 노랑/주황, 시안/틸) 있음.
데이터: 공개된 LeRobot 데모, 과제당 250개 (모션 플래너로 수집).
정책: π0.5 (LeRobot, lerobot/pi05_base에서 미세조정), bf16, gradient checkpointing, chunk 10, 5 step 실행,
      batch 16, GPU 7 한 장 (40GB 상한).
평가: 과제당 50 에피소드 (t52는 추가로 100개 → 총 150), 고정 시드 4242424242부터.

벤치마크 쪽에서 발견해 고친 것 (모든 실험의 전제)
  (a) 물리 백엔드 불일치: 데모는 CPU 물리로 수집됐는데 공식 평가는 GPU 물리. 데모 행동을 그대로 재생하면
      CPU 8/8 성공, GPU 0/8 (IK 계산 차이로 2.5~4.5cm 어긋남). → 데이터와 같은 CPU 물리로 평가.
      공식 프로토콜에선 전문가 시연조차 0점이라, 문헌의 Long 과제 점수가 거의 0인 원인으로 보임.
  (b) 영상 압축 불일치(C420): 학습 프레임은 yuv420 영상에서 디코딩돼 색 해상도가 절반(작은 색 물체가
      2x2 블록으로 뭉개짐). 온라인 관측은 원본 RGB. → 평가 서버에서 같은 yuv420 색 다운샘플을 적용(C420=1).
  (c) 대기 중 팔 흔들림(DEADBAND): 데모는 대기 중 행동이 정확히 0인데 정책은 미세하게 계속 움직여 팔이
      흘러가고 가짜 이벤트를 만듦. → 서버에서 |a|<0.02이면 팔 행동을 0으로 (DEADBAND=0.02).
      t51 v2 노트 15k: DEADBAND 0.001에서 0.90 → 0.02에서 0.96.


1. 출발점: 학습된 메모리는 왜 실패했나 (10/18~10/19)
----------------------------------------------------
아이디어: GRU/Transformer/이벤트 쿼리 같은 학습형 메모리를 정책에 붙임.
결과: 처음부터 학습하는 정책은 정답 큐 색을 직접 알려줘도(oracle) 찍기 수준. 진단해 보니 메모리가 큐 색이
      아니라 "에피소드 지문"(나무 결 등 장면 고유 특징)을 외워 학습 데이터에서만 맞히는 지름길 학습이
      일어남. 병목이 2개(색→위치 대응, 기억 유지)였고, 250개 데모로는 둘 다 안 됨.
전환: 사전학습 VLA(π0.5)는 언어 지시문을 강하게 따르므로, 기억을 "지시문에 붙는 텍스트"로 바꾸면 정책 쪽은
      새로 배울 게 적다는 판단. 실제로 π0.5 + 정답 노트("The cue color was red.")는 t51에서 0.98.
      → 남은 문제는 "정답 노트를 사람 없이 자동으로 쓰는 것" = 이벤트 노트 연구의 출발.


2. 노트 v1: 이벤트 감지 + 작은 VLM 캡션 (10/19~10/20)
------------------------------------------------------
아이디어
  - 장면이 갑자기 바뀌는 순간(큐 등장/사라짐, 후보 등장)에만 노트를 씀. 로봇 자신의 움직임으로 인한 변화는 제외.
  - 노트는 기존 VLM이 쓰고, 과제 라벨은 전혀 쓰지 않음(과제 비의존).
구현 (notes_vlm/notes.py)
  - EventDetector: 직전 프레임과 비교해 어떤 채널이든 40 이상 바뀐 픽셀 수 c를 셈 (DPIX=40).
    이벤트 조건: c >= 8 (NPIX)  그리고  c >= 4 x (1 + 직전 5 step의 c 중앙값) (RATIO=4, IDLE=5)
              그리고 직전 5 step 동안 엔드이펙터 이동 < 1mm/step (로봇이 정지 중).
    * 평균 차이가 아니라 픽셀 수를 쓴 이유: 데모 영상엔 큐가 사라질 때 화면 전체 밝기가 살짝 바뀌는
      현상이 있는데 온라인 렌더러엔 없음 → 평균 차이 기준은 온라인에서 이벤트를 놓쳤음.
    * 비율 검사를 넣은 이유: 대기 중 팔이 0.01mm씩 흘러가면 그리퍼 가장자리 픽셀이 조금씩 바뀌어
      가짜 이벤트가 생겼음.
  - NoteWriter: SmolVLM2-500M-Video-Instruct, 전체 화면 384px로 키워 "Briefly describe the objects on
    the table." 질문, 최대 30토큰.
  - NoteMemory: 최근 K=8개 노트 유지. 10 step 안에 연속된 이벤트는 같은 변화로 보고 덮어씀(BURST=10).
    동일 노트 반복은 버림.
    * 처음엔 K=4였는데 장면 변화 1번이 2 step 간격 이벤트 2개를 만들어, 학습 에피소드 60%에서 첫 큐 노트가
      창 밖으로 밀려났음 → BURST 병합 + K 확대로 0%.
  - 지시문 형식: "<원래 지시문> Notes: (1) ... (2) ..."
  - 학습 데이터: 데모마다 이벤트 프레임에서 노트를 생성하고, 각 프레임의 task 문자열을 "그 시점까지 쓴 노트"
    로 바꾼 LeRobot 데이터셋 사본을 만듦(notes_vlm/build_ds.py, 영상은 심볼릭 링크).
  - 평가: 정책 서버(lrbridge/server.py)가 같은 감지기·VLM을 온라인으로 돌려 노트를 붙임(NOTES=1).
실험과 결과 (t51, 5색, 찍기 0.20)
  - 노트 없음 0.20(C420 적용 후 0.12), v1 노트 10k 0.70, 15k 0.84, 20k 0.82, 정답 노트 0.98.
  - 학습 데모 노트의 첫 색 단어가 실제 큐 색과 일치: 250/250 (magenta는 "pink"로 씀).
  - 문제: 온라인에선 에피소드당 노트 ~15개(데모는 7개 이하). 큐브를 건드린 뒤 계속 쓰는 잡담성 노트.
다른 과제로 확장 시도
  - t54 모양 기억: 노트 0.26 vs 없음 0.14, 그런데 정답 노트도 0.20 → 4~6px 모양을 정책이 못 봄
    (메모리 문제가 아님). 메모리 실험 대상에서 제외.
  - t65 색 순서 3개: 정답 노트도 0/50. 9개 중 순서대로 3번 정확히 멈춰 터치하는 동작을 못 배움. 제외.


3. 노트 v2: 쓰는 시점 규칙 개선 (10/21~10/22)
--------------------------------------------
아이디어: 변화가 "끝난 뒤" 한 번만 쓰자. 변화가 여러 프레임에 걸치면 최종 상태 하나만.
구현 (notes.Scribe, NOTES_V=2)
  - 이벤트 프레임에서 바로 쓰지 않고, 변화량이 NPIX 아래로 떨어진 첫 프레임(최대 5 프레임 뒤)에서 씀.
  - 이벤트 프레임에서도 엔드이펙터가 정지해 있어야 함. 시작 직후(이력 없음)에도 이벤트 허용.
  - BURST 병합 없음 (NoteMemory(0)).
결과
  - 데모의 이벤트 수: t51 에피소드당 정확히 3개 (큐 / 큐 사라짐 / 후보 등장).
  - t51 v2 노트: 10k 0.86, 15k 0.90, DEADBAND 0.02로 0.96 (정답 노트 0.96과 같음).
  - 하지만 t52(9색)는 단독 학습 시 0.02~0.06 (찍기 0.11), 노트 없음 0.08.


4. 노트 v3: 노트 품질 측정과 "변화 영역 확대" (10/22~10/23) — 사용자 지적 이후
-------------------------------------------------------------------------------
계기: "노트 내용이 실제 이미지랑 안 맞고, 로봇 얘기를 할 때도 있다."

4-1. 먼저 측정 도구를 만듦 (notes_vlm/note_bench.py)
  - t51+t52 데모에서 이벤트 프레임 3종(큐 장면, 빈 테이블, 후보 장면)을 뽑음.
  - 큐 색 정답: 큐 장면과 빈 테이블 장면의 픽셀 차이 영역에서 밝은 면 평균 → 가장 가까운 환경 색.
  - 지표: 큐 장면 노트의 첫 색 단어가 정답(동의어 허용)인가 / 빈 테이블을 비었다고 하는가 /
    로봇이나 없는 물체(monitor, keyboard, toy 등)를 언급하는가.
  - v2 노트(500M, 전체 화면) 측정: 큐 색 0.86, 빈 테이블 → 100% 엉뚱한 물체("흰 모니터, 검은 키보드"),
    전체 노트의 36%가 로봇/환각 물체 언급. 사용자 지적이 정확했음.

4-2. 시도 1: 더 큰 VLM, 전체 화면 (n=80 큐 장면)
  - SmolVLM2-2.2B 전체 화면: 큐 색 0.79, 빈 테이블 인식 0.00, 환각 0.07
  - Qwen2.5-VL-3B 전체 화면: 큐 색 0.62, 빈 테이블 인식 0.01, 환각 0.25
  → 모델을 키워도 해결 안 됨. 원인은 모델이 아니라 입력: 4px 큐는 384px로 키운 전체 화면에서도 작고,
    화면 위쪽을 로봇이 크게 차지함.

4-3. 시도 2: 테이블만 자르기 + "로봇 무시, 비었으면 empty라고 답하라" 프롬프트
  - SmolVLM2-2.2B 테이블 crop: 빈 테이블 인식 1.00이지만 큐 색 0.47, 큐 장면도 "비었다" 42%
  - Qwen 테이블 crop: 큐 색 0.00 (항상 "비었다")
  → 환각은 없앴지만 4px 큐를 놓침. 프롬프트만 바꾼 전체 화면은 큐 색 0.71 / 빈 테이블 1.00.

4-4. 시도 3 (채택): 바뀐 영역만 잘라서 확대 (zoom_bench.py, change_bench.py)
  - 이벤트 직전 프레임과 이후 프레임의 픽셀 차이 마스크 → 가장 큰 연결 영역(4번 팽창 후 라벨링)만 남김
    → 그 영역 중심으로 최소 24px 정사각형(여백 6px)을 잘라 NEAREST로 384px 확대.
  - 큐 crop에서 SmolVLM2-2.2B 큐 색 0.96. 9색 구별력(색별로 다른 이름이 나오는 비율) 0.80.
    시안/파랑, 틸/시안은 구분되기 시작함. 남은 혼동: maroon→"red", orange→"yellow".
  - 두 이미지(전/후)를 한 번에 주고 "무엇이 바뀌었나" 물으면 나타남/사라짐을 자주 뒤바꿈(pair_bench.py)
    → 전과 후 crop을 따로따로 묘사하게 함.
  - 프롬프트에 색 이름 목록을 넣었더니 빈 crop에서 목록을 그대로 읊음 → 목록 제거, 예시 2개만 남김
    (prompt_bench.py).

4-5. v3 최종 설계 (notes.ChangeNoteWriter, NOTES_V=3)
  - VLM: SmolVLM2-2.2B-Instruct.
  - t=0: 장면 노트. "What objects are on the wooden table? Name each object with its color, e.g. 'a red
    cube'. Ignore the robot arm. If there is nothing on the table, answer 'The table is empty.'"
  - 이후 이벤트: 변화 영역 crop 전/후를 각각 "List the objects in the image with precise color names, e.g.
    'a cyan cube, a maroon cube'. The wooden surface is not an object. If there are no objects, answer
    'nothing'."로 묘사 → "Change: <전> -> <후>."  변화 영역이 너무 작으면(4픽셀 미만) 노트를 안 씀.
  - 정지 판정 강화: 엔드이펙터 위치뿐 아니라 자세·그리퍼까지 모든 성분 변화 < 1e-3 (Scribe(full=True)).
  - 마스크는 "이벤트 프레임에서 바뀐 픽셀"만 누적 (변화가 가라앉는 사이 로봇이 움직인 픽셀은 제외).
  - 데모 예시 (t52): "a red cube." / "Change: a red square -> brown." /
    "Change: a wooden surface -> a red cube, a green cube, ...".
4-6. v3 품질 측정: 빈 테이블 환각 1.00→0.00, 로봇/환각 언급 0.36→0.00, 큐 색 0.86→0.96, 9색 구별력 0.80.
4-7. 온라인 문제와 대응
  - 팔이 정지해 보여도 관절 공간에서 미세하게 움직여 crop에 팔이 찍힘("toilet", "dog" 같은 노트)
    → 전 성분 정지 판정 + 주 연결 영역 + DEADBAND 0.02. 대기 구간 노트는 데모 구조(3개)와 같아짐.
  - 큐브를 건드리는 조작 단계의 노트는 여전히 가끔 엉뚱함(이 시점엔 이미 선택이 끝나 영향은 작음).

4-8. 결과: t52 단독 학습은 v3로도 0.04. 진단(20 에피소드, 각 큐브까지 최소 거리 기록 기능을 evaluate.py에
     추가): 큐브까지는 19/20 도달하지만 정답 색은 1/20. 노트 문제가 아니라 색 이름→큐브 대응을 못 배움
     (색당 데모 ~28개).


5. 세 과제 공동 학습 (10/23)
---------------------------
아이디어: t50/t51/t52는 같은 기술(색 이름 → 같은 색 큐브)을 공유하므로 데모 750개를 합쳐 정책 하나로 학습.
구현: tools/merge_ds.py (LeRobot aggregate_datasets). 노트 데이터셋 3개를 합침.
결과 (20k, 과제당 50 에피소드)
  - v3 노트: t50 0.96, t51 0.84, t52 0.38 (단독 0.04 → 0.38)
  - 노트 없음: 0.14 / 0.14 / 0.06
  → 같은 데이터·스텝에서 노트 효과 +0.82 / +0.70 / +0.32.


6. 상한선과 통계 보강 (10/26~10/28)
---------------------------------
6-1. v2 노트 공동 학습 (노트 품질 효과 분리): 0.86 / 0.86 / 0.50. → 더 깨끗한 v3가 t52에서 오히려 낮음.
6-2. 정답 노트 상한선
  - 데모 큐 색을 9개로 클러스터링해 이름 부여(maroon, teal 추가로 9개 모두 다른 이름).
    평가 때는 첫 프레임 큐 픽셀로 같은 이름을 붙임 → 시뮬레이터 정답과 150/150 일치 확인.
  - 결과: 0.96 / 0.98 / t52 0.80 (50개) → 추가 100개 0.90 → 합계 0.87.
6-3. t52 150 에피소드 합산 (95% 신뢰구간)

9. 다른 논문과의 성능 비교
-------------------------
주의: 직접 같은 조건의 숫자가 거의 없음.
  - 대부분의 메모리 논문(MemoryVLA, GMP, Chameleon, SimpleMemVLA)은 원래 MIKASA의 RememberColor3/5/9
    (Long 아님, 대기 짧음, 다른 데이터 수와 평가 프로토콜)를 씀.
  - 우리는 VLA용 Long 버전 + 데이터와 일치하는 CPU 물리로 평가.

같은 벤치마크(MIKASA-Robo-VLA, Long)
  - 벤치마크 논문(2610.00604)의 π0.5 기준선: RememberColor5-Long 0.30 (20 에피소드, 찍기 0.20),
    3/9색 Long은 미평가, 14개 과제 평균 0.21, Long 과제 평균 0.017.
  - 우리 t51(5색 Long): v2 노트 단독 0.96, 공동 0.86; v3 공동 0.84; 정답 노트 0.98.
    단, 우리는 CPU 물리라 그쪽 GPU 물리 수치와 완전히 같은 조건은 아님(그쪽 조건에선 시연조차 실패).
  - RePlanMem-VLA(2610.22556): 같은 벤치마크지만 우리가 읽은 범위에선 이벤트 감지/기억 유지 지표만 있고
    과제 성공률 표는 없음.
다른 버전(Long 아님)의 RememberColor 3/5/9 성공률 (참고용)
  - Chameleon(2603.24576): 94.4 / 72.2 / 53.3  (현재 찾은 최고 RC9)
  - GMP(2604.18933): 80 / 61 / 17
  - SimpleMemVLA(2609.05533): 71 / 58 / 59
  - 원 논문의 VLA들(Octo, OpenVLA, π0): RC3 0.35~0.59, RC9 0.06~0.15
  - 우리 (Long 버전): VLM 노트 0.86~0.96 / 0.84~0.86 / 0.41~0.50, 정답 노트 0.96 / 0.98 / 0.87
  → 대략 3·5색은 최상위권 수준, 9색은 Chameleon(53)보다 약간 낮음(VLM 노트 기준). 단 과제 버전이 다르므로
    논문에서는 "참고"로만 쓸 수 있고, 직접 비교하려면 원래 RC3/5/9에서도 돌려야 함.

    우리: VLM 노트 41~50%, 정답 노트 87% (t52).


10. 연구로서의 평가 (솔직한 의견)
---------------------------------
좋은 점
  - 통제된 실험 구조가 깔끔함: 같은 정책·데이터·스텝에서 메모리 형식만 바꿈 (없음 / VLM 텍스트 v2·v3·v4 /
    이미지 / 정답). 상한선과 하한선이 있어 간극의 원인을 정량적으로 말할 수 있음.
  - 효과 크기가 큼: t52 0.08 → 0.50 → (상한) 0.87, t51 0.14 → 0.86.
  - 정책 구조를 바꾸지 않고 기존 VLA에 붙는 방식이라 실용적이고 설명 가능함(노트를 사람이 읽을 수 있음).
  - 부수 발견도 가치 있음: 벤치마크의 물리 백엔드 불일치(전문가도 0점), 영상 압축 불일치, 대기 중 흔들림.
약점 (리뷰어가 지적할 것)
  - 일반성: 지금 제대로 동작하는 과제군이 색 기억 하나뿐. 모양(t54)·순서(t65)는 정책 동작 한계로 제외.
    IROS 수준이 되려면 다른 메모리 유형(셈: BlinkCount, 물체 추적, 순서) 최소 1~2개가 더 필요.
  - 노트 성능이 VLM 색 어휘에 묶여 있음 (9색 0.41~0.50). 원칙적으로 메울 방법이 아직 없음
    (v4 결과, 시각 메모리 개선이 관건).
  - 손으로 정한 감지 임계값(고정 카메라, 정적 장면 가정)과 DEADBAND 같은 보정이 있음.
    "과제 비의존"이라 주장하려면 다른 과제에서도 같은 값으로 동작함을 보여야 함.
  - 시드 1개, t50/t51은 50 에피소드. 최종 표는 시드 2~3개가 필요.
  - 새로움 위험: 이벤트 기반 메모리 쓰기 자체는 KEMO, EventVLA, RePlanMem-VLA 등에 있음. 언어 메모리도
    RoboMME, MEM에 있음. 새로운 부분은 "같은 쓰기 시점에서 형식 비교(텍스트/사라진 것만/이미지 crop/정답)"와
    "보이는 것을 적으면 방해된다"는 분석 쪽이라, 이 부분을 더 단단하게 해야 함.
종합: 방향은 괜찮고 핵심 결과(노트 구조 효과 + 상한선 + 원인 분석)는 논문 뼈대가 될 만함. 다만 지금 상태로는
  "한 과제군에서의 사례 연구"에 가까워서, IROS 제출 전까지 (1) 과제 다양성 (2) 9색 간극을 줄이는 원칙적 방법
  (3) 시드·통계 보강이 꼭 필요함.
