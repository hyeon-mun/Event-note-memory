- 비슷한 색 쌍: red↔maroon, yellow↔orange, cyan↔teal (env 색 index 0↔6, 3↔7, 5↔8).
- "맞는 큐브"는 가장 가까이 다가간 큐브가 정답 색인 경우입니다. 성공은 여기에 터치 조건까지 충족해야 합니다.

해석:
- **선택 (v3→v4):** 후보 색을 모두 나열한 출현 노트를 빼자 "그 밖" 오류가 20→4로 줄었습니다.
- **표현 (v4→v6):** 측정 색으로 비슷한 색 쌍 혼동이 13→5로 줄었습니다. 그런데 "그 밖" 오류가 다시 늘었습니다.
- **활용 (v6):** "그 밖" 오류 12건을 포함해 다른 큐브로 간 17건 모두 단서 노트의 색은 맞았습니다.
  - 대부분 blue/aqua/teal 사이입니다. t=0 장면 노트("a blue cube")가 측정 색 노트("Gone: a aqua cube")와 충돌하는 것으로 보입니다.
  - v7(장면 노트 제거)로 검증 중입니다.
- **v5의 교훈:** CSS4 어휘는 이름 경계가 너무 촘촘해서, 학습 때와 온라인 렌더에서 같은 색이 다른 이름이 됐습니다(예: blue/mediumblue). 어휘는 "너무 정밀하지 않게" 정해야 합니다.
- 그림: `docs/figures/rc9_error_bars_ko.svg`

- **keyframe (11/4):** 사건 시점 전체 프레임을 추가 이미지로 넣은 시각 메모리(RePlanMem 방식)는 단일 단서 9개 평균 0.078로 노트 없음(0.118)보다도 낮습니다. 9개 중 8개에서 노트 없음 이하입니다(RC9-L만 0.06 vs 0.04). RC-Long의 crop 시각 메모리와 같이, 정책이 추가 이미지를 쓰지 않습니다.
- 단일 단서 기억(색, 모양, 모양+색)에서는 효과가 크고, 여러 단서를 다루는 과제(Bunch/Seq/Chain)는 0입니다.
  - Chain3은 이전 실험에서 정답 노트를 줘도 0%였습니다. 기억보다 동작(9개 큐브를 순서대로 터치하고 버튼 누르기)이 병목입니다.
- 노트 품질 관찰:
  - TimedTransfer는 에피소드당 이벤트가 약 97회라 노트 대부분이 잡음입니다.
  - BlinkCount는 깜빡임마다 노트가 생기지만 최근 8개만 남아 많이 깜빡이면 잘립니다.
  - ShellGame의 섞임은 노트로 기록되지 않습니다.

## R7. 노트 내용 통제 C1 (RC-Long v6, t5x 20k, 50 에피소드, `tools/swap_follow.py`)

온라인 "Gone:" 노트의 색 단어를, 장면에 있는 다른 후보 큐브의 색으로 바꿨습니다. t=0 장면 노트는 바꾸지 않았습니다.

| 조건 | RC3 | RC5 | RC9 |
|---|---|---|---|
| 정상 노트 | 0.96 | 0.94 | 0.48 |
| 틀린 색 노트 | 0.44 | 0.64 | 0.34 |
| 틀린 색: 가장 가까이 간 큐브 (정답 / 노트의 색 / 기타) | 28 / 22 / 0 | 35 / 15 / 0 | 19 / 14 / 17 |
| 빈 노트 | 0.26 | 0.10 | 0.08 |
| (참고) 노트 없이 학습한 base | 0.14 | 0.14 | 0.06 |
| 정답 색 노트 (온라인 Gone 노트 색을 정답으로 교체) | 0.90 | 0.94 | 0.60 (정답/쌍/기타 34/7/9) |

- 정답에 가지 않은 에피소드는 RC3, RC5에서 전부 노트에 적힌 틀린 색 큐브로 갔습니다(22/22, 15/15). 정책이 노트를 읽고 따른다는 직접 증거입니다.
- 노트를 비우면 노트 없이 학습한 base 수준으로 떨어집니다. 성능 향상이 노트 내용에서 온다는 뜻입니다.
- 색 이름을 정답으로 고쳐도 RC9는 0.48 → 0.60에 그칩니다. oracle로 학습한 정책(0.80)과의 차이 중 약 1/3만 색 이름 오류 때문이고, 나머지는 정책이 노트를 쓰는 방식에서 생깁니다.
- 일부가 여전히 정답으로 가는 것은 바꾸지 않은 t=0 장면 노트가 정답 색을 담고 있기 때문으로 보입니다.
